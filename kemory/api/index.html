Base URL, auth and conventions

Every endpoint below is served by the Kemory API. Paths are given exactly as the service exposes them; prepend your deployment's origin.

ConcernDetail
Content typeapplication/json on request and response, except artifact upload (multipart) and artifact download (binary stream).
VersioningREST endpoints live under /api/v1. The MCP transport lives at /mcp/v1. Discovery documents sit at the root, where the specifications require them.
AuthA bearer token on Authorization, or X-API-Key for registered agents. See below.
ErrorsConventional status codes with a JSON body. 401 unauthenticated, 403 authenticated but not permitted, 404 absent or outside your tenant — the two are deliberately indistinguishable.

Of the operations listed on this page, most require a credential. The unauthenticated ones are health, OAuth discovery, and the signed-URL artifact stream — that last one carries its own signature in the URL precisely so a binary can be fetched without a bearer.

Scoping is not a filter you can opt out of

Every tenant-scoped read has WHERE org_id = <caller's org> applied at the ORM layer, not in individual handlers. A memory belonging to another tenant does not return 403; it does not appear at all. The same holds for user_id: memories are scoped to their owner, and the shared namespace means "every agent of this user", never "every user".

Compaction — how a memory is compressed over time

A memory is not stored once and left alone. It moves through tiers, each one a cheaper representation of the same content, and the tier it currently occupies is recorded on the memory itself as metadata._compression_tier.

TierWhat it isWhen it happens
L1The verbatim memory as written.On write. Every memory starts here.
L2An AAAK encoding of the single memory — a compact structured form of that one item.Scheduled shortly after write, per memory.
L3A narrative summary spanning several memories in a namespace.Once a namespace has enough new material to be worth summarising, and the new material is novel enough to change the picture.
L3.1LLM-synthesised concepts over the summaries.Above the synthesis threshold, over the L3 layer.
L4Concepts plus Cognition OS graph entities. Not a stored tier on the memory — it is assembled on read.On request.

You can read a namespace at any of these levels through GET /api/v1/namespaces/{namespace}/compressed, choosing with mode: raw (L1), aaak (L2), concept (L3.1) or cognition (L4). merge_mode selects the latest state or the full history.

AAAK is a storage and export format, not a prompt-token saving one. It is measured in bytes. Reaching for aaak to shrink a prompt is a misreading of what the tier is for — concept is the one that reduces what a model has to read.

Two thresholds decide whether an L3 summary is produced at all, and they are the usual reason a namespace sits at L2 for longer than expected: there is a minimum number of new memories since the last summary, and a novelty floor — if fresh memories closely resemble what an existing summary already covers, the run is skipped rather than spending a model call to say the same thing again. A quiet namespace therefore stays at L2 indefinitely, which is correct, not a stall.

Summarisation is bounded: a single run draws on a capped number of source memories rather than the whole namespace. Consolidation policy per namespace, and the stats showing what actually ran, are exposed under Consolidation.

Search summary — the service behind enhance

This is the one most often asked about, because it is not obvious from the path. It is not a separate service: it is POST /api/v1/search/unified with the summary opted in.

The call returns the top ranked hits across memories, chats and text-native files, and — when asked — a short narrative summary written over those hits. The Kora browser extension's enhance action uses exactly this: it searches on the user's draft plus recent conversation turns, takes the top handful of results, and appends them to the prompt as a delimited, provenance-tagged context block alongside the summary. Nothing rewrites the user's draft; the model is given context and left to decide.

The invariant that matters

The summary may only describe hits that were actually returned. Its sources array lists the ids it drew on, and those are a subset of the results in the same response. This is not a stylistic preference — it is what stops the summary from asserting something the user cannot click through to and verify. Clients that filter results after the fact must drop the summary too, or it will outlive the hit it was describing.

The summary is opt-in for a plain reason: it costs a model call, and a caller that only needs a count or a list should not pay for prose. Summaries are cached briefly per user and query.

Degrading honestly

If the summary cannot be produced, the response carries results with no summary rather than failing. A caller should treat the summary as decoration over the results, never as the result itself.

User context — what the vault knows about someone

GET /api/v1/user/context returns a cross-namespace summary for the authenticated user, assembled from the compressed tiers rather than by reading every memory. It is the fast "catch me up" read that agents call at the start of a session, and it takes a depth so a caller can ask for a cheaper or richer answer.

At its richer depths this is an L4-style read: one synthesis pass across the per-namespace summaries. That pass degrades gracefully — if the model call fails, the response comes back without the synthesised layer rather than erroring, so a caller must treat the summary as an optional enrichment over the namespace data, not a guaranteed field.

GET /api/v1/user/profile is the narrower, persisted view: static preferences plus a dynamic part maintained as memories accumulate.

Keeping this page honest

The endpoint tables on this page are generated from the running service's own OpenAPI document by scripts/generate_api_reference.py in the Kemory repository. They are not maintained by hand, because a reference covering this many operations drifts the moment someone adds a route — and a docs page that is quietly wrong is worse than no page at all, since it is trusted.

Regenerate after any route change. The narrative sections above are hand-written and describe behaviour a schema cannot express; they need a human when the behaviour changes.
